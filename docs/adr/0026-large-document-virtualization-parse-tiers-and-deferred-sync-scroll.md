# ADR 0026: 大文档性能优先的虚拟化、解析分档与同步滚动延期

## 状态
已接受 (Accepted)

## 上下文
- 预览层实际把 `parsed.blocks` 全量展开为 GPUI 元素；1.5MB / 36,000 blocks 的 Markdown 实测约 4.7GB RSS、98% CPU。ADR 0002、MVP spec 与 tickets 均声称预览已虚拟化，但代码未接线。
- 编辑器同样全量渲染每一行；默认视图是 Split，因此只修预览仍会被编辑器拖高。
- `sync_map` 每次编辑都重建，但从未被读取；Split 的“同步滚动”实际没有实现。
- 撤销栈固定 100 步、每步保存整篇文本；1.5MB 文档潜在额外约 150MB。
- ADR 0025 的副顶栏/版心部分获准本轮落地；语法高亮、智能抽屉、嵌套列表等继续后置。

## 决策
1. 预览使用 GPUI `list(ListState)` 做可变高度虚拟化；编辑器使用 `uniform_list` 做固定行高虚拟化，只渲染视口与 overdraw 范围。
2. `Document.parsed` 改为 `Arc<ParsedDocument>`，让列表闭包廉价共享 AST；编辑器行缓冲使用可共享句柄，避免逐帧复制全部文本。
3. 解析按体积分档：<2MB 使用 100ms 防抖；2–10MB 使用 300ms；>10MB 暂停自动解析，显示横幅，由按钮、保存或切换到 Preview/Split 触发一次解析。打开文件时先解析一次以显示内容。
4. 代码块改为单个 `StyledText`（行号与代码分两列），避免单个超大代码块在一个列表项内展开逐行元素树。
5. 撤销栈按总字节上限（8MB）裁剪，同时保留最多 100 步。
6. 本轮不实现 Split 同步滚动；移除 app 内 `sync_map` 字段与逐次重建，保留 core 的 `SyncScrollMap` 与测试，并修正文档中“已同步”的表述。
7. UI 只做三件事：删除源码/预览的 32px 副顶栏；源码光标信息改为编辑器右下角悬浮胶囊；预览内容按 `Preferences.max_column_width` 居中。智能抽屉、语法高亮、嵌套列表、代码复制修复后置。
8. 验收：1.5MB 文档 RSS <300MB；新增 `scripts/bench_memory.sh` 记录默认与大文档基线；单测覆盖解析分档、撤销字节上限和脏状态。

## 考虑过的替代方案
- **全量渲染 + 文件大小护栏**：改动最小，但违背 ADR 0002，正常大文档仍不可用。
- **预览用 `uniform_list`**：块高度不一，会裁切或错位。
- **后台线程解析 + 版本号**：更流畅，但 1.5MB 解析实测仅 26ms，100ms 防抖已足够；本轮不引入并发与取消逻辑。
- **立即实现同步滚动**：兑现产品承诺，但与性能目标冲突，且需要双向滚动事件与高度测量，风险明显更高。

## 后果
- 正面：大文档内存从 GB 级降到百 MB 级；滚动与输入可用；大纲跳转精确；单个大代码块不再爆炸；界面少两条 32px 横条并恢复舒适版心。
- 代价：Split 仍不同步；>10MB 预览需手动刷新；单个超大表格/列表仍可能偏高，记录为已知限制；代码块改为整体文本后，逐行交互与当前实现不同。
- 文档：实现完成后用实测值修正 README 的 `<50MB`、`120fps`、`Synchronized Split View` 等表述；ADR 0025 的其余项保持未实现。

## 实测结果（2026-10-28，macOS release）
`./scripts/bench_memory.sh`（8 次采样峰值）：

| 场景 | 空闲 RSS |
| :--- | ---: |
| 默认示例 | 85–93 MB |
| 1.5 MB / 16,546 标题 | 136–148 MB |

多次运行存在约 10% 波动；验收线 300 MB 已满足。默认示例仍高于早期 `<50MB` 宣传值，文档已按实测更新。
