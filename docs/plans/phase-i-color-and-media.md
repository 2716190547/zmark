# Phase I：灯箱颜色根因、结构化代码高亮与本地图片

状态：用户已确认整体规划并授权先执行 I0；灯箱独立验收通过后再推进 I1–I3，尚未修改生产代码。2026-11-03。协调与回调 `w3:p9`、执行 `w3:p8`、独立审查 `w3:p7`。

## 已确认的产品选择

- 源码围栏代码与预览共用语言感知的语法高亮，不再用整块统一墨色代替结构区分。
- 首期验收 XML/HTML、Java、Python、JavaScript、JSON、YAML、SQL、Shell、Rust；未知或未支持语言回退普通代码色，不误称已支持。TypeScript/TOML 不作本批专项保证。
- 无语言及 text 围栏保持纯文本，不自动猜语言。保留现有代码换行规则：非空且非 text 的语言块换行，空语言/text 横向滚动，Mermaid 独立处理。
- 默认与 Claude 使用暖米灰代码背景、低饱和紫色标签/关键字、金色字符串、灰色注释。其他六套调色板保持自身风格，全部适配明暗；正文颜色与字体不随代码主题修改。
- 显示实际本地 Markdown 图片，支持相对文档目录和绝对文件路径；本批不增加网络图片请求。按可用宽度保持比例，加载失败才显示占位及原因，不把占位视为加载成功。

## 已证实的灯箱根因

实际生产链路：

```text
预览 img(path)
  → 文件资源 ImageAssetLoader
  → SVG render_pixmap
  → swap_rgba_pa_to_bgra

灯箱 img(ImageSource::Image(Image::from_bytes(Svg, ...)))
  → ImageDecoder
  → Image::to_image_data
  → SVG render_pixmap
  → 直接把 RGBA 预乘像素作为 BGRA 的 RenderImage
```

GPUI 0.2.2 本地源码：`elements/img.rs` 的 ImageDecoder::load 直接调用 to_image_data；文件资源 SVG 分支才执行 swap_rgba_pa_to_bgra；`platform.rs` 的 ImageFormat::Svg 分支没有通道交换或 alpha 还原。Phase G 更换 API 仍回到同一错误解码路径，之前 ADR 与验收对“新路径会自动转换”的判断不成立。

最小实际解码对照已运行，SVG 含不透明 `#9370db` 和 60% alpha 的 `#ecf2dc`：

| 像素 | 字节 Image 路径（当前灯箱） | 文件路径（当前预览） |
| --- | --- | --- |
| 紫色 | [147,112,219,255] | [219,112,147,255] |
| 半透明浅绿 | [142,145,132,153] | [219,241,236,153] |

两路应为同一 BGRA 颜色，但真实返回不同；测试红灯并直接比较实际 RenderImage::as_bytes，不是源字符串或 API 名称断言。

诊断产物：`/private/tmp/glidemark-color-probe/color_probe.rs`、`result.log`；已编译运行命令 `/private/tmp/glidemark-color-probe/color_probe --nocapture`，结果 0 passed / 1 failed。这是生产使用的 GPUI 两种解码入口对照，不是完整灯箱 UI 截图测试。

深浅 SVG 选择、HiDPI 缓存、图表源 classDef/style 和卡片底色也需回归，但不能用它们掩盖上述已证实的像素错误。第三张附件日期为 11-02，仅作为现象参考；当前真机窗口读取超时，尚未完成新版本视觉复现。

## 其他事实

- 预览 render_code_block 只设置 syntax_code，StyledText 仅加选区背景，没有语言词法着色。
- 源码 tokenize_code_line 只有通用关键字/引号/注释猜测，未接收围栏语言，不识别 XML 标签、属性及跨行语法状态。
- Markdown Image 分支始终渲染图标和 alt/url，占位不是本地文件找不到的充分证据；当前没有普通图片实际加载链路。

## 工单与验收顺序

### I0：先闭环灯箱像素

将当前红灯对照固化为永久回归，在真实 open_lightbox 所用的加载结果上检查不透明色、半透明色及合成底色。优先复用已转换正确的 GPUI 公共文件资源解码，不新造手动颜色转换；如采用其他实现，必须以真实像素证明等价。

先验证所选加载方案能同时管理缓存和 GPU 纹理释放，再替换生产路径。现有资源释放仍必须成立：关闭、文档切换、图片替换均释放旧纹理及资产缓存。不要为修色放弃显存回收，也不要假设 GPUI 文件解码的内部缩放不会扩大 HiDPI 纹理预算；检查真实解码尺寸与最终内存预算。

同一原始 Mermaid SVG、当前明暗变体、自定义颜色和透明度在预览与灯箱保持一致，不通过改 SVG 源色抵消通道错误。热缓存、重开、切主题、切文档和不同屏幕倍率均应正确。像素检查通过后补真实应用视觉对照，记录能实测与不能实测的部分。

### I1：共用语法解析与色彩语义

仓库没有现成的语言解析依赖。方案优先采用成熟 Rust 语法库 syntect，复用其内置语法；采用最小必要 feature，不加载无关主题/HTML 导出/运行时语法文件，不手写九套语言词法规则。纯 Rust regex 后端可避免新增 C 编译链，实际性能在接入前测量。

官方依据：[syntect 文档](https://docs.rs/syntect/5.3.0/syntect/)、[feature 列表](https://docs.rs/crate/syntect/5.3.0/features)、[项目说明](https://github.com/trishume/syntect)。TypeScript/TOML 并非内置包的专项保证，本轮不额外添加语法集合。

源码与预览共用语言及带范围的语义结果；支持跨行注释/字符串/嵌套语法状态，XML 的 tag、attribute、string 不混为一色。复用 ThemeColors 的关键字、字符串、注释色，按需要补充属性/数字等最少语义。未知范围回退代码普通前景。

仅改文字前景与代码背景，不额外改变字体、字重、行高或插入内边距。高亮范围必须使用合法 UTF-8 边界，软折行、选区叠加、纯文本复制与实际点击几何不变。

解析按文档/代码内容及语言复用，多行语法正确失效，不在每个 render 或每次滚动解析整篇。设置合理预算及失败回退，避免恶意或巨大代码块阻塞 UI；异常时显示原代码，不能丢内容。验收相同语言代码在源码与预览中得到一致语义和颜色，不能只有 helper 正确而两侧生产入口未接通。

### I2：暖色代码主题

浅色初稿：背景 `#F6F5EF`、标签/关键字 `#7D56B3`、属性 `#596A88`、字符串 `#8A6B12`、数字 `#995B2B`、注释 `#676D65`。这些是待视觉验证的设计值，不冒充截图精确采样。

全部前景对实际代码背景的对比度应达到 4.5:1。深色单独适配，另外六套调色板沿用自身风格，文本选区叠加后仍可辨识结构颜色。通过真实 Maven XML 源码/预览截图对照，而不是只判断色值字段存在。

### I3：本地图片实际加载

将 Markdown URL 与当前文档路径一起传入预览加载链路，按文档父目录解析 `./assets/...`，不使用进程 cwd 假充基准。草稿无文件目录时相对图片给出明确失败状态，绝对路径仍可用。

复用 GPUI 图片加载与缓存，优先覆盖 PNG/JPEG/WebP/GIF/SVG 的已有平台支持，实际解码能力逐项验证。加载不在 render 同步读完整大文件，约束解码尺寸与内存，支持中文/空格路径；混排图片不丢失前后文字。失败显示原因和原引用，不把图片成功渲染变成一行 URL。

图片出现后的高度变化须正确更新虚拟列表和同步滚动；原文选区、图片 alt 的纯文本语义、代码复制、Mermaid 灯箱均不回退。本批不扩展普通图片的新灯箱交互，不增加远程下载。

## 分工与交付门槛

先完成 I0 并独立验收，再推进高亮/配色及图片；源码/预览多个工单共享文件时只允许一个写入者，主执行代理统一接入 Workspace。独立测试与实现并发，原始失败检查及关键回退检查要可重复执行。

最终验收同时包括像素对照、真实渲染色块/代码范围、实际本地图片加载，以及 Phase H 默认全量与独立 21 项事件回归。新上色不能牺牲已经艰难修正的文字几何和选区判别力。

整体规划已获用户确认，先派发 I0，未验收前不推进其他生产改动。文档与 ADR 中的旧颜色结论已纠正为问题重开，不提前标记修复完成。实现后的测试、提交、本机打包和独立终验继续遵守现有流程，不 push、不建 PR。

诊断探针直接比较 GPUI 的两种入口，用于证明依赖行为差异；正确修复应用后，这个依赖对照仍可能失败。永久回归应改为调用真实 open_lightbox 并取得最终显示像素，与预览正确路径比较，不要求修改 GPUI 源码或伪造探针结果。
