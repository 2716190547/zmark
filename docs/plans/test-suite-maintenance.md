## 最小精简规则

先做一张小型覆盖清单：测试/所保行为、是否经过生产入口、现有替代、耗时来源、保留/合并/删除理由。仅列实际候选，不新增通用测试管理框架。

1. 删除已证实恒真或测试自造结果的断言；若该行为没有有效替代，先用最小可运行行为检查补上，再删旧检查。
2. 同一行为和失败模式重复覆盖时保留判别力更强的一项；helper 的算法边界与生产接线检查职责不同，不因名称相近就合并。
3. 删除约束无关实现细节、没有持续产品契约的源码字符串检查。合法的资产/格式/不可变约束仍按价值判断，不一概禁用 include_str!。
4. 测试只用一次的样板就地缩减；不为了少几个文件建立复杂 fixture 层或新依赖。
5. 不靠 ignore、放宽断言、缩小输入、移到默认不跑的 feature 或删掉失败用例实现“精简”。不设强制删减比例，不为每个简单测试增加变异脚本。

保存与文件错误处理、中文输入/焦点、真实文字命中、预览选区/复制、同步滚动、灯箱颜色/解码预算及异步陈旧结果等历史关键行为保留。它们可以有更短、更强的替代，不能失去保护。

## 运行节奏（已独立批准）

- **开发与中间提交**：运行当前修改的算法检查，以及调用链上的生产行为回归。按具体目标使用现有 cargo test 的包/目标/名称选择能力，不引入自动受影响分析系统。记录所跑命令与尚未运行的范围；有限验证提交不等于可交付。
- **共享链路改动**：例如 editor、preview、workspace、theme、核心 AST 或公共布局，扩大到其相关历史行为；不能机械地只跑最近工单名称。发现失败或无法可靠划定影响范围时直接扩大到全量。
- **阶段提审与打包前**：对精确候选运行 cargo test --workspace，加项目要求的 feature 专项回归；Phase H 21 项与 Phase I 28 项通过同一条多目标命令串行运行（`--test-threads=1`），分组报告、重叠去重。I0 元素加载与颜色检查包含在有效全量中。全绿后提交、打包及独立验收；候选代码变化后重跑受影响检查，并在阶段最终候选上补齐完整门槛。
- **独立审查**：变更范围决定深挖与反例，不要求每次重做所有历史变异实验。删除旧测试时证明保留下来的检查仍能发现对应关键故障；涉及 I0 颜色归因或真实选区接线的改动，应复验相关已知变异。当前明确要求的验收不因本计划自动取消。
